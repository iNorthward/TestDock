# 平台序列化与反序列化规范

版本：1.1 · 2026-10-03 · 适用于新增或修改接口案例、响应校验器、请求构造器、OAS 与 wire 清单。


## 1. 分层与三种表示

| 归属 | 负责 | 不负责 |
| --- | --- | --- |
| Core 平台 | OAS 结构解析、保留完整联合约束、通用严格校验、配置加载与四态结果 | 推断项目金额/ID 必须是哪种类型，写死框架阈值 |
| 项目 Adapter | 实际 HTTP/JSON 解码方式、认证/信封、项目序列化策略与可复用项目校验 | 用宽松强转把声明/实现冲突变成通过 |
| 业务 Pack | 策略来源、schema/字段映射、样本、金额单位/精度/舍入、ID 正数或非负等业务约束 | 把数据库类型或单个响应样本当作完整线上契约 |

每个字段区分三种表示，分别验证：

1. **请求表示**：query/path/header 是 HTTP 文本编码，JSON body 有真实 JSON 类型；服务端参数绑定/反序列化决定接收方式。
2. **响应表示（wire）**：线上 JSON 的 string/number/bool/null/object/array；由真实输出序列化链路决定。
3. **业务/DB 表示**：int、Decimal、数据库 DECIMAL/BIGINT、时间对象；只用于类型校验通过后的业务计算/对账。

响应 ID 为字符串不说明请求 ID 也应改成字符串；数据库 DECIMAL 不说明响应一定是 JSON number；Python Decimal 是业务对象，不是线上 JSON 类型。请求和响应复用 schema、但线型不同的，必须拆开 schema 后再同步，禁止直接改共享 schema 影响另一方向。

当前同步器遍历请求 body、操作及路径级参数、组件引用、嵌套/联合字段、callback 与 webhook 的方向归属。若响应策略将改变请求也可达的 schema，整个同步在写入 OAS/wire 文件前拒绝，并要求先拆分方向；未解析的引用报告 incomplete，不绕过保护。方向核验在副本上进行，冲突不会留下前面已处理 schema 的部分修改。

OAS/wire 写入由 `scripts/output_transaction.py` 同时锁定两条输出路径，在各自目录暂存、备份、fsync 后逐份替换。第二份提交失败时回滚；恢复失败保留事务记录，后续正常调用或 `sync_json_wire_types.py --recover` 恢复。`--check` 遇到未完成事务返回 incomplete，且不修改输出。相同路径、硬链接别名、最终符号链接或非法输出路径在写入前拒绝；恢复时核对完整指纹，不覆盖外部改动。

这是 POSIX 上可恢复的两文件提交：每次 rename 只对单文件原子，未取得同一锁的读取者仍可能在两次替换之间看到不同版本。进程强制退出后要到下一次恢复才回到一致状态；journal 落盘前的中断可能留下暂存文件。当前机器已验证提交与恢复故障，未验证跨文件系统故障或断电；后续契约版本包应通过单一激活指针解决读取的一致视图。

## 2. 生成案例前的证据表

每个需核验的字段至少在案例说明、接口画像或修复记录中登记下表。可引用已审计的 Pack 清单，避免重复复制。

| 项 | 必填内容 |
| --- | --- |
| 身份 | Pack、method/path、请求/响应方向、schema 名与字段路径（包括数组层级） |
| 声明 | OAS 快照路径、版本/更新时间、type/format、required、nullable/联合分支、pattern/范围 |
| 实现 | 显式字段注解、继承/内部类、实际 mapper/converter、全局模块与配置；框架版本/来源 |
| 校验 | 采用哪个 helper/项目策略；必返、null、空字符串、零、正负和边界分别如何判断 |
| 计算 | DB 字段、单位、金额 scale/舍入或容差、时间单位/时区、映射依据 |
| 验证 | 对应离线测试与受影响 SAFE case ID、结果、未执行项 |

字段注解与全局模块的覆盖关系须按该框架实际实现核实，不能只看“有没有注解”。序列化策略清单应记录版本、启用配置、依赖/实现证据；版本或配置漂移时重新核实，不沿用旧观测兜底。

OAS 是接口声明，并非独自证明实际线型的证据。源码也不能独自证明运行部署的配置。用实现/框架证据与少量授权只读响应相互核验；响应示例只说明一个样本，不说明全集或边界。

## 3. 冲突处理与结果状态

- OAS、实现、实际响应或断言不一致时，分别保留声明、证据和失败值，先定位有误的一侧。业务应有契约仍有效；不能因为实现这样返回就自动接受业务缺陷。
- 已有明确契约且实际违反：`failed`。只读测试先确认 HTTP 状态与 Adapter 成功/拒绝行为，再判字段契约。
- 缺少必要证据、策略、身份或 schema：`incomplete`；基础设施失败使用平台已有错误状态处理，不能伪装成案例通过。`uncertain` 是候选属性，不是已验证契约。
- 禁止把类型断言改成 `str(x)`、`int(x)`、`float(x)` 后比较，或“number/string 都收”来消除失败；修正 OAS/断言必须有证据记录。
- 禁止自动刷新在线 OAS 后覆盖已确认本地基线；同步策略/清单后先检查差异，再运行定向验证。

## 4. 请求序列化与反序列化

- 根据请求 schema 与项目请求构造器设置 JSON body 类型；金额 body 是字符串还是数字由该请求契约决定。不能用响应 serializer policy 覆盖请求模型。
- query/path 的文本编码与 JSON body 的数字类型分别处理。参数声明 integer 时 URL 上仍是文本，不能据此要求响应字段也为 integer。
- 正向案例使用规范输入；非法字符串、指数、超范围、错误 Content-Type、缺失/null 等进入明确的异常案例，按项目反序列化与校验行为断言。禁止客户端提前纠正非法值，导致没测到服务端。
- 使用现有 API session/项目请求构造器与 JSON 编码入口；Decimal 不能直接交给普通 JSON 编码器而默认转 float。需要数字金额时采用经确认的无损编码方案，不使用 `default=str` 将全部未知对象都变成字符串。
- 响应必须先保留 HTTP 状态、Content-Type 与未经字段强转的 JSON 解码值。项目如采用 `parse_float=Decimal` 等解码策略，需显式声明并与校验 helper 配套；不要在个别案例偷偷换解码器。

Core `api_client.ResponseDecoder.decode_json(text, method, url)` 支持 Adapter 注册或会话显式注入；成功与 HTTP 错误响应使用同一解码策略，二进制与 parse error 行为保留。预解码的测试 transport 仍负责自己的解码，不由 Core 再次转换。无损工具 `lossless_json_loads` 用 `JsonDecimal` 保存小数/指数的原始 JSON token，整数保持 Python int、字符串保持 str；`json_number_amount` 接受这个已解码 number 标记，但拒绝普通 DB Decimal、bool 和字符串。未经原始线型校验，不把任何 Decimal 冒充 JSON number；解码结果也不能直接充当请求编码策略。


## 5. ID 与整数规则

- JSON string ID 与 JSON integer ID 用不同校验策略；Python bool 是 int 子类，业务整数校验须排除 bool。
- 数字文本是否允许正号、前导零、空白、指数、零、负数及最大值分别按契约判断；不得仅调用 `int(value)`。平台严格 int64 字符串 helper 拒绝这些非规范形式，并检查 int64 范围。
- 框架按值域输出不同类型时，OAS 必须保留类型和范围的完整联合约束。`oneOf` 恰好满足一个分支，`anyOf` 至少满足一个；不能选第一个分支，也不能去掉边界仅变成 string/integer 混收。
- 平台候选携带完整 `schema`；联合字段的候选 `type=union` 表示需按分支约束校验，不是 JSON 的第七种类型。顶层或 data 的联合结构同样保留。
- JSON Schema 的 integer 与语言解码后的 Python 类型并不等同。本仓 `json_integer` 对 int64 范围内的 Python int 做严格校验并拒绝 float；使用它须对应已确认的项目输出与解码策略，不能把这项更严策略说成所有 OAS 的默认规则。
- 展示/浏览器计算不得把可能超出 JavaScript 精确整数范围的 ID 转 Number；DB 对账只能在原始 wire 校验通过后转换为 int，保留原值供定位。


## 6. 金额规则

| 已确认的线型 | 应验证 | 计算表示 |
| --- | --- | --- |
| JSON number | 解码策略所表示的数字、排除 bool、拒绝 NaN/Infinity；合法范围按契约 | 校验后用 Decimal；保留浮点解码精度限制 |
| 普通十进制字符串 | 字符串类型、普通十进制语法、有限值；指数是否禁止按策略 | Decimal 原字符串 |
| 可含指数的十进制字符串 | 字符串类型、允许的指数语法与有限值，例如项目确认的 `0E-8` | Decimal 原字符串 |

- 三种线型不得任意混收。普通字符串字段不能因为另一个字段允许 `0E-8` 就跟着允许指数。
- 不先 `float` 再比较；JSON number 若已被客户端解码为 float，`Decimal(str(value))` 不能恢复线上已损失的精度。精度敏感接口需项目明确解码/传输策略；不能仅因转换后相等就证明无损。
- 金额数值相等与格式相等分开：`"1.0"` 与 `"1.00"` 数值可能相等，但契约若规定 scale 或格式，仍需另验；不自动去零、舍入或截断。
- 对账使用 `money_eq` 或现有对账 helper，明确单位、汇率、scale、舍入与容差来源；不随意扩大容差。必返/null/空值/负数/零等业务约束另验，零不等于缺失。
- DB helper 保留驱动返回的 Decimal；正数化或减手续费不得先转 float。缺失金额/手续费保留不可计算状态，不因 `or 0` 伪造有效到账金额。严格 parser 返回 Decimal(0) 是校验成功，须用 `is not None` 判定，不能依赖真假值。
- ID、金额、日期是不同语义；不得复用金额强转规则处理 ID，也不得根据字段名称猜序列化策略。

## 7. 原始类型检查后才做业务转换

```python
from json_wire_types import positive_int64_string, finite_decimal_string

# 例：仅用于已确认 id 为正 int64 字符串、amount 为普通十进制字符串的项目字段。
# required 与 nullable 需要先按该案例契约校验；不能用 .get() 混淆缺失和 null。
assert "id" in row and "amount" in row
identifier = positive_int64_string(row["id"])
amount = finite_decimal_string(row["amount"])
assert identifier is not None, "id 原始线型或值域错误"
assert amount is not None, "amount 原始线型或语法错误"
# 此后才把 identifier / amount 与业务及 DB 值比较；保留 row 原值。
```

`schema_wire_errors` 只检查已出现、非 null 的已登记数值字段，不替代 required/nullable、完整 JSON Schema、数组形状或业务断言；它检查为空不说明整个响应已通过。

## 8. 配置、统一入口与执行清单

- OAS 解析统一用 `openapi_contract.py`；保留嵌套 `$ref`、oneOf/anyOf 全分支与值域。外部/循环引用、无效组合或暂不支持的 allOf 冲突明确报告，不能丢字段后继续宣称覆盖。
- 新增/修复案例依次核实证据表 → 选择 helper → 校验存在性与原始线型 → 转换/业务对账 → 同步文档 → 定向测试。
- 测试至少覆盖一个合法值、相反 JSON 类型、bool、缺失/null（适用时）、零/负数/范围边界，以及涉及金额指数/scale、联合约束的代表分支。不同 JSON 类型造成的失败不得计为后端缺陷，先检查声明与实现证据。
- OAS、wire、serializer 等契约资源须在 Core/Pack 定向回归清单登记；资源文件改变不能以“不是源码”为由选择零测试。具体输入路径及覆写通过 Pack `input_keys` 映射，规则见[平台执行隔离与任务规范](平台执行隔离与任务规范.md)。
- 平台变更运行相关离线回归和有限接口候选预览；业务案例按授权执行受影响 case ID 的 SAFE。遵守用户的耗时范围，不运行全部案例。报告分别列通过、失败、未执行、数据变更。

## 9. 标准依据与项目证据

- [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html)：JSON 类型、数字和精度互操作边界。
- [OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.0.html)：请求、响应与 Schema 声明。
- [JSON Schema 组合规则](https://json-schema.org/understanding-json-schema/reference/combining)：allOf/anyOf/oneOf 的匹配语义。
