# 长任务证据配方

在临时目录运行两个阶段的合成导入。示例使用平台的任务存储、请求号查询、协作取消和 SQLite 历史。源数据、导入副本和所有报告都属于该示例。

```sh
example_dir="$(mktemp -d)"
python3 -B examples/task_evidence/demo.py --output "$example_dir/evidence"
```

每轮建立独立目录。先写入 `plan.json`，记录轮次 ID、请求 ID、输入 SHA-256 和阶段依赖。任务以请求 ID 去重，使用计划内容摘要绑定输入。首次报告 `first-report.json` 保留当时的结果，最终报告 `report.json` 另存后续核验和清理结果。跨轮次概览位于 `summary.json`。

| 合成情形 | 应留下的证据 |
| --- | --- |
| 成功与清理中断 | 两阶段通过后，先记录清理意图，再模拟移除示例副本后中断。此时报告仍是未完成。重新清理时核验副本已不存在，保存当次凭据，随后重复清理也只核验状态。 |
| 执行失败 | 导入失败与未运行的输入检查分别可见。详细日志达到示例预算时只保留限额内的细节，独立的首条失败和结果仍完整。 |
| 协作取消 | 已开始的任务收到取消请求，在下一次写入前检查并退出。轮次未完成，后续步骤及待清理状态可见。 |
| 已产生结果但回复未确认 | 通过请求号读取旧回执，导入阶段保持未完成。计划允许独立进行输入检查，原写入只发生一次。新输入与旧计划不符时另存 stale 记录。 |

真实项目应在 Pack 中明确阶段依赖、副作用校验、日志预算以及清理动作。启动后如果服务状态未知，先查持久回执，再按照 Pack 的确认方式核验业务副作用。只有依赖都已满足的阶段可继续。等待超时、缺少原回执和清理缺证分别保留为待核验。

示例的总览 `ok` 表示四种合成情形符合预期。每一轮自身的失败与未完成状态仍保存在报告及历史中。示例只对自己的目录写入，没有业务服务或真实数据参与。
